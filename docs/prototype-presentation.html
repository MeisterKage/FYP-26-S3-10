03

The project scope

  • The goal is to build a news publishing platform on which every published article carries a Credibility Score, and every contributor a Accuracy Rate, both produced by a fixed formula whose inputs are disclosed to the reader rather than by a hidden or predictive model.
  • The system covers the full editorial lifecycle:
    • Drafting, submission, scheduling and publication of articles
    • Editorial review scoped to an assigned content category
    • Reader reporting of inaccuracies, and moderation of what is reported
    • Corrections and retractions, logged permanently against the article
    • Contributor appeals against a correction, resolved by an administrator
    • Premium subscriptions and a tiered contributor revenue share
  • Six user tiers hold different permissions, from an unregistered visitor who can only read to a system administrator who governs the scoring thresholds themselves.
  • Deliberately out of scope for v1: machine-learned credibility prediction, semantic search, image and video analysis, multi-language publishing, and native mobile applications.

The scope is bounded by a single design rule: if a reader cannot be shown why a score is what it is, the feature that produced it does not belong in v1.

04

Learning objectives

Explore industry tooling

Work with the stack a graduate would actually meet: a single-page React front end against a REST API, a relational database under versioned migrations, automated tests in continuous use, and a real cloud deployment rather than a localhost demonstration.

Improve technical skills

REST API design, six-tier role-based access control, password hashing and token sessions, schema migration, input sanitisation, rate limiting, and writing tests that fail for the right reason.

Practise team engineering

Shared version control with reviewed commits, a documented design system so that two people produce one interface, and formal SDLC documentation that stays in step with the code rather than describing an older version of it.

The objective that shaped the project most

Learning to say no. A credibility platform invites feature after feature — sentiment analysis, bias detection, automated fact-checking — each of which would have made the score unexplainable. Holding the line on a disclosed, arithmetic formula was the hardest engineering decision of the project, and the one the rest of the design depends on.

05

Findings and research

We examined six products that assess or publish news, to establish what already exists and where a gap remains.

NewsGuard

Journalist-assigned trust ratings for whole publications, nine weighted criteria. Rates the outlet, never the individual article.

Ground News

Aggregates one story across outlets and shows the political spread of coverage. Measures bias, not accuracy.

Media Bias / Fact Check

Manually maintained directory of outlet bias and factual reporting. No publishing function, and updates lag.

Full Fact

Charity fact-checking of individual claims, with automated claim detection. Checks claims after publication elsewhere.

Substack

Independent publishing with paid subscriptions and a revenue share. No accuracy signal of any kind.

Medium

Open publishing with editorial curation and a partner programme. Curation is discretionary and undisclosed.

The gap

Every product we examined does one of two things: it rates outlets without publishing them, or it publishes writers without rating them. None scores the individual article, ties that score to the writer's own track record, and shows the reader the arithmetic. That intersection is the product.

Development tools

Back end — Python 3.12 and Flask

Flask is the single entry point to the system; no client ever queries the database directly. SQLAlchemy for the ORM, Alembic for versioned migrations, Argon2 for password hashing, PyJWT for sessions, bleach for HTML sanitisation on write, Flask-Limiter for rate limiting.

Database — PostgreSQL via Supabase

The PDD specifies MySQL. The team moved to Supabase-hosted PostgreSQL for a managed instance the whole team can share without each running a local server. Row Level Security is enabled on all 23 tables and default privileges are revoked, so a leaked key alone reads nothing.

Front end — React 18 with Vite

A single-page application in plain JSX with hand-written CSS against a documented token file. No component framework, so that every rule in the design system is one we can account for.

Hosting — Render

Two services from one blueprint: the built front end as a static site, and Flask under gunicorn as a web service. Supabase holds the database only — it cannot serve a website, so the two are complements rather than alternatives.

Testing — pytest and Playwright

139 automated test cases covering the scoring engine, the permission middleware, the editorial workflow, error handling and rate limiting. A batched Playwright pass captures every screen at desktop and mobile width and fails on console errors or horizontal overflow.

Version control and environment

GitHub for source control, with the environment file held out of the repository. Visual Studio Code as the editor across the team.

One deployment constraint worth recording: the API runs a single gunicorn worker, because the rate limiter holds its counters in process memory. Two workers meant two independent counters and a limit that was twice as loose as configured.

10

Scheduling

Waterfall — for the deliverables

The subject's milestones are fixed and sequential: requirements, design, prototype, final product. The waterfall model matches those dates and is how we plan against the assessment calendar.

Scrum — for the development itself

Inside each phase the work runs as short sprints against a backlog of user stories, because requirements did change: the database moved from MySQL to Supabase, and the accuracy formula was rewritten after testing showed it punished new writers eight times harder than veterans.

Our prototype — the scoring engine

A reader is never shown a bare number. Every article carries the ledger that produced it: what the writer's record contributed, what the sources added, and what each correction took away.

The score is a fixed arithmetic expression. The inputs are named in public; the tuning weights are internal and administrator-configurable, so no constant may be hard-coded into the interface.

Accuracy is smoothed, not a raw ratio

A plain ratio of clean articles to published ones cost a five-article writer 15.0 points for one correction, against 1.9 for a forty-article writer — a 7.9× penalty for the same mistake. Blending the rate toward a platform baseline reduces that gap to 4.4× and removes the cliff where a single article moved a whole back catalogue.

Worked example — a published article

Contributor accuracy record+ 63.75
Verifiable sources (5 × 5, capped at 25)+ 25.00
Logged corrections (1)− 15.00
Retraction− 0.00

Band: Moderate — 60 and above

Bands are High, Moderate, Low and Disputed. None is signalled by colour: the band word is always rendered and is always the authority, so the reading survives greyscale printing and colour-blind vision.

Rich-text editor with source tagging, draft and submission workflow, scheduling, per-article status, and an accuracy rate that updates as the record changes.

Review queue scoped to assigned sections, flagged-content queue with every reader report shown in full, correction logging, and a dispute queue for appeals.

Nine tabs: accounts, applications, editor assignments, platform-wide article moderation, disputes, categories, scoring thresholds and the audit log.

Security testing against the deployed system: injected scripts stripped on write, every privileged route refused to a free reader, tampered session tokens rejected, and sign-in and password-reset responses byte-identical whether or not the account exists, so neither can be used to enumerate users.

14

Future development

Security

Two-factor authentication for editor and administrator accounts; email verification at registration; moving rate-limit counters to shared storage so the API can run more than one worker.

Account management

Real transactional email for password resets and notifications, which the prototype currently logs rather than sends.

Payments

A real payment gateway in place of the stubbed integration, and scheduled payout runs against the tiered revenue share.

Scoring

Per-category weights, since a science article and a sports report do not carry the same sourcing expectation; and a public history of threshold changes, so a score movement can be attributed to a policy change rather than to the writer.

Editorial

Cover images, comment moderation, and a duplicate-content check surfaced to editors during review.

Expansion

A native mobile client, and multi-language publishing with per-language editorial assignment.

Three documentation amendments are also outstanding: the PDD still specifies MySQL, Figure 5.96 states that threshold changes do not affect existing scores when in fact they recalculate, and Figure 5.87's "remove articles" is implemented as unpublish rather than delete, because a corrected article is the record of that correction.
